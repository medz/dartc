# 纯 Dart 原生编译器架构

本方案定义一套独立、可由 Dart 持续演进自身的原生 AOT 工具链，让运行时成本随实际能力引入。主线是语言实现、自举、自托管和可替换的执行基础；静态库、动态库及其他原生组件能力作为后续有限扩展，通过已有 FFI 契约表达边界。编译器、链接器、标准库（std）和运行时源码采用 Dart；指令编码、启动跳板和底层原语由 Dart 代码生成。先实现 macOS ARM64，IR 与语言语义不绑定 Mach-O 或 ARM64。

本方案是架构设计，不表示相应编译器和运行时已经实现。语言兼容、自托管、性能和体积分别验收。

自托管验证工具链能否支撑自己的实现；原生组件能力直接解决宿主如何调用 Dart 的问题，可以在自托管前独立实现与验收。无托管需求的导出应允许零 Dart 运行时初始化；需要对象、GC 或调度的导出则提供显式上下文与生命周期，成本和线程约束写进 ABI。不能把所有组件都强制变成带 main 的独立应用。

本文描述目标架构，实际实现将逐步对齐；当前支持范围与使用方法以 [README](../README.md) 为准。

## 用 Dart 持续演进执行基础

最终成品必须允许用 Dart 继续开发 Dart 自己的执行基础。自托管是打通链路的第一个里程碑；降低固定运行时成本只是其中一项收益。编译器、内存管理、线程调度和启动流程应能以 Dart 实现、修改和替换，并逐步改善执行模型、性能、并发和冷启动。

| 实现内容 | 主要表达方式 |
|---|---|
| 优化、指令选择、寄存器分配 | 普通 Dart 编译器代码 |
| 分配器、GC、对象布局、运行时数据结构 | Dart 算法与显式原生内存操作 |
| 线程池、锁、调度器 | Dart 算法、系统线程接口、原子操作和明确的内存序 |
| 栈切换、寄存器恢复等特殊操作 | 少量语义清楚的编译器原语，确有需要时提供汇编出口 |

优先复用 dart:ffi 的原生类型、指针和布局能力。可以等价转换的操作由编译器实现，不能等价转换的类型和原生目标由使用者通过 FFI 显式声明。不得通过隐式转换改变 Dart 语义，也不另造一套重复的原生类型体系。

底层库需要可检查的不依赖 GC 的代码，以及原子操作、内存序和受控的机器状态接口。它们必须足以支撑用 Dart 重写分配器、GC 和调度算法；大部分运行时算法不能固化为手工机器码模板。后端仍负责机器指令编码，运行时算法则保持为可独立修改的 Dart 源码。

自托管之后的演进链路为：已有 dartc 编译改进后的 Dart 编译器与运行时，得到新版 dartc，再由新版重建自身并验证行为。引入新的底层原语时，先用旧版本已有能力实现识别和编译该原语的新版编译器，再让运行时开始使用它，保留可恢复的引导节点。

本文的模块和 ABI 可以随实现经验调整。当前能编译自身的语言子集、运行时启动约定和进程级 arena 都不代表最终语言兼容性或运行时设计已经完成；最终验收还包括一般 Dart 程序所需语义、可改进的运行时和上述自我演进能力。

## 架构基线

| 项目 | 设计选择 |
|---|---|
| 语言 | 首个兼容基线固定为 Dart 3.13.5；按库声明的语言版本处理版本化语义 |
| 编译模式 | 原生 AOT，默认封闭程序分析；动态边界必须声明 |
| 前端 | 独立实现扫描、解析、名称解析、类型系统、流分析和常量求值 |
| 中间表示 | 类型化 SSA IR 和 Machine IR；AST 不是第三套优化 IR |
| 泛型 | 默认共享代码并保留运行时类型实参，按代价模型选择专门化 |
| 对象表示 | 64 位 tagged 值，未压缩引用，固定对象头与数据化类描述符 |
| GC | 每个 isolate 独立堆，精确、非移动、停止该 isolate 执行的标记清扫 |
| 异常 | 基于帧描述符与处理表展开，正常调用不额外返回异常状态 |
| 原生互操作 | 独立的目标 C ABI 分类器、调用跳板、回调与根句柄 |
| 原生产物 | 可执行文件；逐步扩展目标文件、静态库和动态库，原生 ABI 由显式 FFI 声明确定 |
| 链接 | 应用、标准库和运行时按符号依赖共同裁剪 |
| 实现组织 | 一个编译器包，内部目录按职责分组；标准库和目标运行时源码独立 |
| 自举 | 官方 Dart 构建宿主编译器，再用新编译器构建相同的编译器源码 |

语言语义和公开 标准库 API 是兼容目标；官方 Kernel、AOT 快照、VM embedding ABI、Flutter engine ABI 不作为兼容接口。反射、动态代码加载、JIT 和热重载不是本 AOT 平台的默认能力。涉及动态装载的能力需要独立的平台契约，不能一边承诺开放世界语义，一边按封闭世界删除实现。

Dart 3 的正式规范尚未覆盖全部当前特性，因此兼容基线同时使用规范、已接受的特性规范、参考实现和语言测试，不能只依赖一份规范 PDF。[Dart 语言规范入口](https://dart.dev/resources/language/spec)

各模块的边界如下。

| 模块 | 输入 | 输出与约束 |
|---|---|---|
| driver | 源文件、包配置、语言版本、TargetSpec、产物种类、优化策略 | 构建请求与诊断；不实现指令和对象布局 |
| frontend | 源码依赖图 | 解析并完成语义检查的 ResolvedProgram；不依赖目标 CPU |
| ir | 已解析的实体与类型 | SSA 的数据结构、合法性规则、遍历和打印 |
| analysis | SSA 与根集合 | 分析结果；不修改程序 |
| optimize | SSA、分析结果与代价模型 | 修改 SSA，并报告哪些分析失效 |
| lower | 已检查程序或已优化 SSA、ABI | 分阶段展开高级语义；不计算文件地址 |
| backend | 完成表示选择的 SSA、目标 ABI | 可重定位的代码片段与元数据 |
| link | 代码、数据、符号引用和根集合 | 裁剪后的 LinkedImage 与稳定地址布局 |
| format | CodeBundle、目标文件或 LinkedImage | 目标文件、静态归档或可装载映像；不决定语言行为和寄存器分配 |
| abi | 目标参数与普通 Dart 数据定义 | 编译器和运行时共享的固定契约；不依赖前端和优化器 |

依赖只沿数据流向下，analysis 和 optimize 依赖 ir，frontend 与 format 不互相导入。运行时入口的签名和效果由 abi 定义。运行时实现不能导入编译器前端、优化器或后端。

宿主编译器通过它所运行的平台 SDK 使用文件和进程服务；std 与目标运行时是编译输入。新编译器通过库映射把 dart:core 等名字定位到 lib/src/std 下的源码。宿主入口不导入目标标准库与运行时的底层实现；目录位于 lib 中并不会使它们自动进入宿主构建。宿主和目标源码使用各自的解析与静态分析配置。

初始入口使用直接函数调用与固定阶段。只有增加真实的第二个目标时才抽出必要的共用目标逻辑，不先建立插件注册框架。

## 前端阶段与语义边界

递归下降是本项目可继续采用的解析方式。需要分离的是语法识别、名称绑定、类型判断与代码生成的职责，而不是为更换解析算法建立一套新框架。

| 阶段 | 输入与输出 | 拥有的职责 |
|---|---|---|
| scanner | 一个源文件 → 带文件身份与位置的 tokens | 注释、标识符、字面量、运算符和词法错误；不查符号、不选择运行时函数 |
| parser | tokens → 语法 AST | 声明、类型写法、表达式、语句和库指令；保留名称与源位置，不分配局部槽、不发射 IR |
| resolver | 库图与 AST → 符号绑定及语义注解 | 库可见性、作用域、名称遮蔽、参数与成员绑定、类型规则和必要流分析 |
| typed lowering | AST、绑定、类型与语言配置 → SSA | 保持求值顺序，展开语言结构，形成显式调用、控制流、对象操作及效果 |

AST 只记录语法结构，例如调用的目标表达式、实参和类型实参；它不因一个名称恰好叫 `print` 就选择输出指令。类型写法同样先保留为语法节点，之后才解析为语义类型。绑定和类型可以保存在同一棵 AST 的注解表中；`ResolvedProgram` 是这些结果的组合，不要求再复制一棵“类型 AST”或增加一套优化 IR。

库依赖由源文件中的库指令建立，保留库 URI、导入前缀和可见性信息，不能靠连接源码字符串获得名称空间。scanner 不负责寻找依赖，parser 不负责决定导入的名字最终指向哪个声明。根源文件和后续发现的依赖使用相同的扫描、解析入口，之后统一交给 resolver。

### 过渡实现与目标的差距

现有前端按文件扫描源码，Token 保留源文件身份与 UTF-16 偏移。库图收集相对导入和导出，保留前缀及 `show`/`hide` 可见性。递归下降 parser 生成声明、类型写法、表达式和语句 AST，不查询语义符号表，也不生成 IR。库符号表处理声明、私有名字、导入和导出；用户声明与受信任的核心库、宿主接口和运行时原语按来源区分。

当前 `binding.dart` 在 lowering 前独立解析函数内的局部值引用。作用域先收集声明，表达式、变量声明与参数保留稳定的声明 ID；参数、函数体、循环和 case 的词法作用域不会随 IR 槽的分配改变。lowering 分别保存声明类型与存储槽，并在声明前引用处报源诊断。field-formal 参数不产生函数体局部名字，wildcard 声明也不遮蔽外层名字。

`flow.dart` 按声明 ID 保存局部变量的当前类型、是否已赋值和路径可达性。lowering 在条件、短路表达式、分支、循环及退出边界传递和合并这些事实；循环先撤销会被写入的变量提升。局部读取使用提升后的语义类型，存储槽仍使用声明类型，并在读取和写回边界转换表示。此实现覆盖当前语法中的局部 `is`、空值判断、`as` 和赋值事实，尚不包含闭包捕获、字段提升、模式或完整的流分析。

`typing.dart` 独立描述已支持核心类型的赋值、条件、接收者和运算符规则，不依赖 AST、IR 或存储槽。lowering 使用当前流类型检查这些规则，再选择表示转换与指令。动态值可以在赋值边界接受运行时检查；Object 和未提升的 nullable 值不能借助隐式强转绕过静态类型错误。运算符结果由静态接收者类型决定，运行时函数采用的 tagged 或原始字返回方式不决定表达式的语义类型。

`??` 保留左侧的一次求值，只在 null 路径执行右侧，并将两条路径的流事实合并。类型检查始终检查两个操作数，上下文类型传入两侧；结果使用左侧非空类型与右侧类型的公共上界，左侧为 Null 时使用右侧类型。常量求值采用相同的选择规则，未执行的右侧仍检查常量资格。

形参 AST 保留必需位置参数、可选位置参数、命名参数、required 和默认表达式。`arguments.dart` 为已绑定的函数、方法和构造器建立实参到形参的对应关系，检查遗漏、重复和未知名字；私有命名 field-formal 的对外名字与实际字段名分开。调用先按源码顺序求值接收者和实参，再按形参顺序填入默认值、交给物理调用约定，超过八个参数仍使用普通栈参数。

`resolve_type.dart` 统一从库符号和类型 AST 解析语义类型，供前端与常量求值共用。`constants.dart` 在声明库中计算常量和默认值，局部 const 通过绑定 ID 读取并使用当前提升类型；参数和非 const 局部不能退回库名字。常量保留表达式静态类型及实际负载种类，声明与默认值同时检查静态兼容性和实际负载。短路及条件表达式的未执行分支仍检查常量资格和类型，但不执行除零等操作。

const List 按完整的实际 List<T> 类型和元素常量值规范化，嵌套列表共享子对象，表达式的较宽静态类型不改变实际常量身份。每个使用到的规范对象通过普通 IR getter 按需构造并缓存，构造完成后由 Dart 运行时标记为不可修改；不可达 getter 不引入集合运行时。默认参数、全局和局部 const 以及独立字面量使用同一常量池。dart:core identical 使用已绑定的核心库符号；常量求值不把同名用户函数当作内建操作。当前还支持标量运算、字符串插值和长度；Map、Set、const 对象及完整常量规范尚待实现。

列表常量 getter 引用紧凑的只读数据，由 Dart 运行时循环构造，避免按元素展开机器码。数据保留完整 List<T> 类型和原始整数位模式；字符串与嵌套 getter 使用相对地址，嵌套 getter 是显式的可达性依赖。只有被引用的数据及其类型、字符串和子 getter 进入产物。未使用全局槽裁剪尚未实现。常量池缓存按当前单线程启动模型工作，多线程发布规则仍需随线程与 GC 契约建立。

`frontend.dart` 仍承担库与成员绑定、字段布局、有限类型判断以及 AST lowering，再由带类型信息的线性栈 IR 提升为 CFG SSA。这条路径尚未形成独立完成全部绑定、类型检查与流分析的 `ResolvedProgram`。

主要需要拆开的耦合如下：

- 类型写法已有独立 AST，`dynamic`、`Object`、`num`、`null` 与 nullable 类型保留独立身份；List 类型实参、协变读写与边界转换已有基础实现。一般泛型、完整子类型关系、动态成员分派和流分析仍不完整。
- 局部值引用已有可复用的声明 ID；顶层调用与实例成员的绑定及类型结果仍在 lowering 时计算，尚未形成完整语义注解。
- 核心库静态成员及 String、List 操作仍有按已绑定类型和成员拼写选择 builtin 的分支，应继续迁移到标准库声明与明确原语契约。
- 条件、循环、赋值和构造器已有 AST；条件上下文的短路逻辑直接形成分支，值上下文保留布尔合流值。lowering 仍分配局部槽并修补线性栈 IR，尚未直接构造 SSA。
- 库版本、package URI、条件导入、part 和多数 SDK 库尚未实现。未支持的库 URI 与导入修饰应在库指令边界报错，不能静默改变可见性或选择另一份实现。

这些是需要逐步替换的实现边界，不是为已有子集补充更多名称分支的理由。

### 绑定后再选择 builtin

resolver 必须先回答一个名称属于哪个库、哪个声明，以及成员和类型实参绑定到哪里。局部变量、用户声明和导入前缀都参与这个过程。用户自己的 `print`、`nativeLoad16` 或同名成员不能仅因拼写相同就获得标准库或底层原语语义。

builtin 表以已绑定的库符号身份及其声明契约为入口，例如目标标准库中的 `dart:core` 输出函数、受信任的内部内存原语，或 `dart:ffi` 中具有显式 NativeType 签名的声明。完成绑定与类型核验后，typed lowering 才能选择普通库调用、受约束的内建操作或等价的直接指令。符号名仍可用于诊断，但不能作为唯一身份。

`String` 和 `List` 的成员、运算符以及 FFI 声明也遵守这一规则。解析器只产生调用、成员访问或运算表达式；接收者类型和已绑定声明决定其语义。标准库实现可以演进，前端不应因此不断增加按成员文本选择运行时函数的分支。原语的签名、效果与可信来源在明确边界核验，内部阶段使用核验后的符号和类型。

### 保持原生自举的渐进替换

先固定源文件身份、token 位置与库指令，再把当前支持的声明、表达式和语句保存为普通 Dart AST 节点。resolver 收集声明并建立作用域，随后逐项接管当前解析过程中完成的绑定和类型工作。AST 节点只在真实语言构造需要时增加，不提前建立通用插件或 visitor 框架。

迁移期间，新的 typed lowering 可以继续输出现有带类型信息的栈 IR，由既有 SSA 提升和后端编译。这只是保留可用后端的适配边界，不把栈 IR 发展为第三套长期优化表示；在语义边界稳定后，再由相同 lowering 直接构造 SSA。两条入口不长期独立实现同一套 Dart 语义。

每次替换保持旧原生编译器能够构建新版，并由新版继续构建自身；已有程序的可观察行为和后续自编译结果用于验证迁移。若 AST 或 resolver 的实现需要新语言能力，先引导该能力，再在自身源码采用。完成一个文件的拆分，不作为整个前端架构完成的判据。

标准库源码同样遵守这条引导链。StringBuffer 的可选初值、write(Object?) 和可选 writeln 参数由普通 Dart 声明和方法实现，使用一般参数绑定及默认值，不由调用方的名称特判补齐。

### 实现参考与组织原则

- [OXC 的 parser 与 semantic](https://github.com/oxc-project/oxc/tree/main/crates)：语法结构与作用域、符号身份分开，语义结果附着已有 AST；本项目保持单一 Dart 包，不复制其 Rust crate 划分。
- [Go 的编译阶段](https://github.com/golang/go/blob/master/src/cmd/compile/README.md)及[原语选择](https://github.com/golang/go/blob/master/src/cmd/compile/internal/ssagen/intrinsics.go)：通用语义先进入 IR，目标相关 lowering 与分配在后；原语选择依赖已经绑定的调用和库身份。
- [Zerolang 的类型核心](https://github.com/vercel-labs/zerolang/blob/main/native/zero-c/src/type_core.h)和[文件映像接口](https://github.com/vercel-labs/zerolang/blob/main/native/zero-c/src/macho_format.h)：类型定义有单一归属，代码、重定位和映像通过明确数据交接；文件封装不回头猜测前端语义。

源码按真实职责分组，需要同一份定义的模块直接 import 其拥有者。内部文件不通过转导隐藏依赖；也不为尚未实现的阶段预建目录、通用基类或注册框架。平台差异只在出现实际差异的位置拆开，公共的数据定义与算法仍共用。

## 构建数据流

```text
SourceGraph（按库保留源文件及依赖）
  → scanner：带源位置的 tokens
  → parser：语法 AST
  → resolver：符号绑定、类型与流分析
  → ResolvedProgram（AST 与语义注解）
  → typed lowering 与结构化语法展开
  → SsaProgram
  → 局部优化与全程序分析
  → 表示选择与运行时 ABI 展开
  → MachineProgram
  → 指令约束、寄存器分配与栈布局
  → CodeBundle
  ├→ 可重定位 Mach-O .o → 静态归档 .a
  └→ 链接裁剪、地址松弛与最终布局
       → LinkedImage
       → 可执行 Mach-O 或 .dylib 与签名

用户显式 FFI 声明 → 经核验的原生边界与入口
```

结构化语法展开负责模式匹配控制流、求值顺序、闭包提升和异步状态机。异步与生成器先展开为普通状态机函数，再构造常规 SSA；其跨暂停状态和 finally 行为在该阶段确定。SSA 可保留 MakeClosure、Allocate、TypeCheck 等高层操作，直到相关优化完成。

当前可执行入口由前端解析入口库暴露的 main 符号，并在需要时生成普通 IR 适配函数，填入可选命名参数及 main 第二位置参数的 null。后端只接收显式入口函数，以及零个参数或一个 List<String> 的启动契约，不根据名字和源参数数量猜测调用方式。

主要接口按下列职责划分；名称和类型表示模块契约，不是已实现的 API。

```dart
Tokens scan(SourceUnit source);
AstUnit parse(Tokens tokens);
ResolvedProgram resolve(SourceGraph parsedUnits, LanguageConfig language);
SsaProgram buildSsa(ResolvedProgram program);
void optimize(SsaProgram program, OptimizationPolicy policy);
void lowerRepresentations(SsaProgram program, TargetAbi abi);
MachineProgram selectInstructions(SsaProgram program, TargetAbi abi);
void allocateRegisters(MachineProgram program, TargetAbi abi);
CodeBundle emitCode(MachineProgram program, TargetAbi abi);
Uint8List writeObject(CodeBundle unit, TargetAbi abi);
Uint8List writeArchive(List<ObjectFile> units, TargetAbi abi);
LinkedImage link(List<CodeBundle> units, LinkOptions options);
Uint8List writeMachO(LinkedImage image, MachOOptions options);
```

所有操作都可以在内存中完成。需要缓存或外部链接时才序列化中间产物，不强制经过汇编文本和磁盘目标文件。

产物种类是构建选项，不为每种产物建立一套编译器。目标文件保留重定位和未解析导入；静态库包装目标文件及索引，不经过最终地址布局。动态库按显式导出集合链接，不要求 main。可执行文件才按应用契约建立启动入口。初版归档按功能单元拆分目标文件，使宿主链接器能够按实际符号抽取。

## 类型化 SSA IR

### 基本结构

SSA 使用基本块参数表示合流值，不另建一套 Phi 指令体系。

| 结构 | 内容 |
|---|---|
| Program | 库、实体、类型、函数、常量和显式根集合 |
| Function | 符号、签名、参数、基本块、源位置和分析版本 |
| Block | 参数、有序指令、一个终结指令 |
| ValueInfo | ValueId、语义类型、表示和定义位置 |
| Instruction | 封闭的具体操作、输入、结果、效果和源位置 |
| Terminator | 跳转、分支、调用的正常与异常出口、返回或抛出 |
| SymbolRef | 函数、类型、字段、常量或原生符号的逻辑引用 |

内部以整数 ID 引用值、块和实体，使用普通 List 与封闭的数据类型，不使用字符串属性字典表达每条指令。先保证可读性和正确性，再通过实际内存与耗时分析决定是否压成并行数组。

函数具有且仅具有一个正常入口。每条可达路径必须由合法终结指令结束；后继基本块的参数个数、类型和表示必须匹配。源位置保留为紧凑索引，用于诊断、内联栈和调试。

示例：

```text
fn f(%condition: bool/i1) -> int/i64:
entry:
  branch %condition, yes(), no()

yes:
  jump merge(10)

no:
  jump merge(20)

merge(%value: int/i64):
  %result: int/i64 = int.add %value, 1
  return %result
```

### 语义类型与机器表示

DartType 回答“这个值是什么”，Rep 回答“这个值如何保存”。两者必须分离。nullable、泛型、dynamic 和运行时类型实参不会因为选择了机器表示而消失。

`num` 保留独立语义类型与 TypeRef，int 是其子类型；List<num> 不因现有元素都是整数就成为 List<int>。当前数值实现支持整数实例及其 num 操作和检查，double、浮点运算与 `/` 尚未实现。num 使用 tagged 表示，已知 int 运算可使用完整 i64；typed int 与 dynamic 相加的结果类型是 num，dynamic 接收者的算术和关系运算结果仍是 dynamic。布尔关系结果进入 dynamic 时必须装箱，而已知 int、bool 结果离开 tagged 运行时路径时必须解箱。

当前 `is`、`is!` 与 `as` 的 AST 分开保存被求值表达式和目标类型。绑定后，类型测试与显式转换以独立 IR 操作携带语义类型 ID；Machine IR 根据目标类型选择 Dart 运行时检查，通用路径接收原生 TypeRef 地址，精确 int、bool 转换直接调用对应解箱检查。测试返回 bool，失败转换保留抛出效果，即使结果未使用也不能删除。局部类型提升独立保存语义类型，不改变声明槽的机器表示。

| Rep | 用途 |
|---|---|
| i1 | 已知的未装箱布尔值 |
| i32、i64 | 整数计算、窄化和原生接口 |
| f32、f64 | 浮点计算与原生接口 |
| ref | GC 可识别的对象基址，可按静态类型允许 null |
| tagged | 可能是小整数、null 或对象引用的 Dart 值 |
| addr | 原生或底层内存地址，不是 GC 根 |
| v128 | 有实际 SIMD 操作时使用的机器向量 |

Rep 不是用户可见的新增 Dart 类型。对象引用与原生地址不能隐式互换。Box、Unbox、类型检查和数值转换是显式操作；Box 可能分配对象、抛出异常并到达安全点。

语言整数、浮点、移位和溢出行为以所选 Dart Native 语义为准。IR 不借用 C 的未定义行为假设，也不默认把 NaN、负零或装箱数值的 identical 行为改成地址比较。

### 操作与效果

操作集合至少包括常量、参数、整数与浮点运算、比较、字段与索引访问、检查、分配、闭包、直接调用、动态调用、运行时调用和原生调用。具体操作使用封闭的带类型数据，而不是万能的 op 加参数 Map。

每个操作与函数摘要记录以下独立效果：

```text
读内存
写内存
可能抛出
可能分配
可能经过 GC 安全点
原生交互
原子或同步操作
```

分配和 GC 不能合并成一个标记：安全点检查可能 GC 却不分配，某些分配快路径也可能暂时不进入收集器。未知调用默认保守地认为可读写内存、抛出并到达安全点。

内存至少区分 Dart 堆、静态状态、原生内存和 I/O 等效果域。块内顺序约束有副作用和可抛出操作；别名分析证明不冲突后才可重排。初版采用值 SSA、有序指令和派生的别名分析，不把完整 MemorySSA 做成每条指令的必需格式。

正常返回和异常转移是显式控制流：

```text
call     已证明不抛出的调用
invoke   具有正常后继与异常后继的操作或调用
jump     向后继传递块参数
branch   条件分支
switch   多路分支
return   正常返回
throw    抛出或向上传播
unreachable
```

invoke 的返回值进入正常块；异常对象与栈轨迹进入异常块。finally 在展开时形成正常和异常路径均会执行的控制流。将 invoke 简化为 call，需要证明它不会发生 Dart 异常。

### 验证

IR 验证器检查定义支配使用、块参数、调用签名、表示转换、异常边、安全点约束与 noGC 约束。优化器不能绕过这些规则。开发模式可在每个变换后验证，正常构建至少在表示选择和后端边界验证。

## 优化与 Machine IR

优化采用固定阶段和少量工作队列。分析有明确版本，变换报告 CFG、调用关系、类型或内存行为是否改变，不重复运行未受影响的全程序分析。

当前布尔检查化简只使用直接的 SSA 定义证明：纯 Bool 装箱的结果再接受 bool 检查或转换时，可重用原来的未装箱 bool。变换重写值和边参数，不移动或删除原值生产者的副作用；仍被 tagged 使用方引用的装箱值继续保留，其他可能失败的检查不变。

Machine IR 选择在常量传播后识别计数为 0..63 的整数移位，形成仅含数值输入和即时计数的操作，不再传递计数寄存器或保留多余的常量指令。其他计数继续使用完整的负值和宽度检查。ARM64 后端按这个证明选择即时移位指令，不在发射阶段重新猜测值范围。

```text
SSA 简化
  → 根与调用关系分析
  → 类型流与动态调用目标分析
  → 内联、常量传播和控制流化简
  → 逃逸分析、对象拆分和分配消除
  → 循环与内存优化
  → 受影响函数重新简化
  → 表示与运行时调用展开
  → 最终可达性清理
```

显式根由启动和导出契约确定。分析新发现的运行时调用、闭包入口、原生回调需求、描述符和类型实参单调加入依赖工作队列；优化改变边后使相关分析失效并重新求闭包，最终不可达节点再删除。不能把一次早期扫描当作最终链接清单。

类型流分析使用有限的保守抽象域。递归泛型或无法维持精度的情况归并为类集合、可空性与类型上界；运行时仍保留精确的类型实参，不能因分析合并而改变语义，也不为无限的运行时泛型实例化生成无限函数体。

泛型默认使用共享函数体和显式类型实参。只有收益足够时才生成专门版本，并保留需要的动态通用入口。内联和专门化受编译速度、运行速度或体积策略约束，不能默认无限展开。

Machine IR 表示目标指令、虚拟寄存器、立即数、地址模式、符号、调用约束、标志位、寄存器读写与 clobber。它不再负责 Dart 名称解析和类型推导。

ARM64 初版使用线性扫描寄存器分配，支持固定寄存器约束、活跃区间拆分、溢出、重载与并行拷贝消解。Machine IR 不承诺始终是 SSA：选择后可保留 SSA，消除块参数与寄存器分配后允许多次定义，最终不得残留虚拟寄存器。

GC 根位置在表示选择、活跃性分析、溢出和栈布局确定后生成。后续移动代码必须同时更新其符号锚点，不能让栈映射继续引用旧偏移。代码生成需要同时考虑栈帧与安全点活跃指针，Go 的后端也明确进行这两项处理。[Go 后端说明](https://go.dev/src/cmd/compile/README)

## 编译器与运行时 ABI

### 唯一定义来源

abi 目录使用普通 Dart 常量与数据定义描述以下内容：

```text
AbiVersion
ValueEncoding
ObjectHeaderLayout
ClassDescriptorLayout
CallSignature
RuntimeEntrySpec
FrameDescriptorLayout
RootMapEncoding
ExceptionTableEncoding
```

编译器、标准库内部绑定和运行时共同使用这些定义。文件偏移和所有类的具体字段偏移不写死在公共 ABI 中，按类布局或最终链接计算。

缓存产物带有 ABI 指纹。它至少覆盖版本、目标平台、字宽、字节序、值编码、对象头、调用规则和元数据格式。指纹不同直接拒绝混链并重新构建。

### 值与对象布局

初版限定 64 位地址、8 字节对象对齐、未压缩引用。采用下列内部编码，和官方 Dart VM 的编码相互独立：

```text
tagged 值最低位为 1：有符号小整数，编码为 (n << 1) | 1
tagged 值为 2：false
tagged 值为 4：true
tagged 值最低位为 0 且大于 4：对象基址
tagged 值为 0：null
```

小整数承载有符号 63 位范围。超出范围的语言整数在需要 tagged 表示时装箱；SSA 内的完整整数运算可以保持 i64。true 和 false 使用立即数，内部已知布尔计算使用 i1。当前这一表示用于 dynamic、Object、可空数值和对应的字段及列表元素；已知引用类型保持未压缩对象地址。

对象头固定为两个机器字：

```text
+0   ClassDesc 引用
+8   布局标志、GC 标记与 identity hash 状态
+16  对象负载
```

ClassDesc 是映像中的只读元数据，记录布局、字段表示、扫描信息、实例大小或变长规则、类型参数位置和保留的分派入口。对象头中的 ClassDesc 引用不是受 GC 管理的 Type 对象。动态对象保存描述符地址；静态对象可用布局标志声明首字保存相对对象基址的有符号位移。统一的描述符访问操作负责解析，静态映像因而不需要为每个对象头增加绝对地址重定位，也能正确参与 macOS 地址随机化。

当前普通实例、String、List、列表 backing array 和装箱整数使用这一对象头。String 的长度位于 `+16`，UTF-16 数据从 `+24` 开始。List 的长度、容量、backing 引用和完整 List<T> 的 TypeRef 地址依次位于 `+16`、`+24`、`+32`、`+40`。backing array 按元素表示区分原始字、引用与 tagged 槽，`+16` 记录已初始化前缀，元素从 `+24` 开始；clear 和 removeLast 同步缩短这一前缀。

List 的布局标志位 1（值 2）表示固定长度，位 2（值 4）表示不可修改。普通字面量创建可增长列表，List.filled 根据显式 growable 参数设置固定长度，const List 同时设置两个标志。协变写入先检查值类型，随后检查不可修改标志，再检查索引范围；读取仍检查范围，改变长度的操作在各自入口检查固定长度限制。运行时内部已知有效范围的循环可直接读取 backing，避免重复检查。

当前 ClassDesc 占 64 字节，保存实例大小、字段数、引用与 tagged 字段掩码、对象种类、类名及 toString 入口。当前 TypeRef 是 32 字节原生只读元数据，记录类型种类、元素类型或 nullable 基类型、类描述符和存储表示；它不是受管理的 Dart Type 对象。TypeRef 边、类名与代码入口采用相对记录基址的位移，映像元数据表的描述符槽相对表基址。按实际依赖保留描述符和 TypeRef。

运行时中的多数引用仍通过原始整数传递，分配器尚未记录可回收的物理分配跨度，托管句柄、安全点根图与精确 GC 也尚未实现；统一对象头和扫描掩码本身不能作为启用回收的依据。运行时类型检查失败目前终止进程，下面的异常与托管调用设计仍是演进目标。

普通实例字段按已知类型采用原始字、引用或 tagged 槽，其 GC 描述符必须与实际布局匹配。数组同样按描述符区分元素表示。

目标中的一般泛型实例应把运行时类型实参保存在负载的显式引用槽并参与 GC；动态构造的 Type 与类型实参数组也应成为受管理对象。当前 List 使用编译期可枚举的原生 TypeRef，不能据此假设所有泛型实例化都可以静态枚举。描述符和缓存表必须正确保留未来引入的托管类型引用。

闭包包含代码入口、环境引用和所需的类型实参。Records 使用编译期可识别的 shape 描述符保存位置字段与命名字段结构，运行时类型仍遵守结构化语义。

### 调用约定

内部托管调用与平台 C ABI 分开定义。已知目标使用直接入口，只有动态调用、闭包通用调用和 Function.apply 等路径需要通用入口。

| 项目 | ARM64 托管调用 |
|---|---|
| 线程上下文 | x28 指向当前 ThreadState |
| 整数、引用参数 | 按展开后的签名使用 x0 至 x7，其余进入栈 |
| 浮点参数 | 按签名使用 v0 至 v7，其余进入栈 |
| 返回值 | 整数或引用为 x0，浮点为 v0；普通复合 Dart 值初版为对象引用 |
| 隐藏参数 | 类型实参、环境和 receiver 显式进入内部签名并参与同一参数分配 |
| 栈 | 16 字节对齐，固定帧头；真实的无调用叶函数可以省略帧 |
| x18 | 不参与分配，保留给 Apple 平台 |
| 寄存器保存 | 遵守目标 ABI 的保存规则；x28 不作为普通临时寄存器 |

x28 来自 AAPCS64 的被调用者保存寄存器集合，但这一托管约定是本工具链自己的选择。FFI 分类器还必须实现 Darwin 对标准 ARM ABI 的具体调整，不能直接套用上述托管参数布局。[AAPCS64](https://github.com/ARM-software/abi-aa/blob/main/aapcs64/aapcs64.rst)、[Apple ARM64 ABI](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms)

动态通用入口采用下列逻辑签名：

```text
invokeEntry(
  tagged receiverOrClosure,
  ref argumentsDescriptor,
  addr argumentVector,
  ref typeArguments
) -> tagged
```

实参向量中的元素是 tagged 值，调用者的根映射描述其活跃范围。ArgumentsDescriptor 记录位置参数数目与命名参数映射，可以是只读映像对象或动态构造的受管理对象；动态调用不能假定它永远是原生地址。编译器按源码顺序求值，再重新排列已求得的值，不能因参数布局而改变副作用顺序。

通用入口校验参数、补缺省值、处理类型实参，并进入直接函数体。只有需要通用调用的函数才生成该入口，避免为每个函数附加固定调用框架。

### ThreadState 与启动接口

ThreadState 是原始内存中的运行时上下文，其受管理引用字段由显式根描述扫描。

| 字段组 | 内容与生命周期 |
|---|---|
| heap | 堆页、大小类别、标记工作区与收集状态的原生地址 |
| roots | 句柄表、静态根表与当前根范围 |
| exception | 待处理异常与轨迹的受管理引用 |
| frames | 托管帧和 ForeignFrame 链的原生锚点 |
| isolate | 所属 isolate、执行者与线程状态 |
| stdState | 调度器、类型缓存等可选受管理状态 |

可执行应用的启动跳板先以无托管上下文的引导调用约定建立原始 ThreadState，再设置 x28，初始化实际需要的堆、根与标准库状态，调用入口函数。入口完成后的退出条件由标准库调度语义决定，包括 Future、消息、定时器和原生资源。库的托管上下文由宿主显式创建，不能在装载时自动启动应用 main。

只有整程序证明全部可达路径都不需要 ThreadState 时，才能采用省略该上下文的启动形式。引导调用本身不能假设 x28 已经有效，也不能先分配依赖尚未初始化的受管理堆对象。

### GC 与安全点

每个 isolate 有独立可变堆，初版采用精确的非移动标记清扫，按大小类别维护空闲块。只读程序映像可以在 isolate 间共享。跨 isolate 的可变 Dart 对象通过复制或有显式所有权转移的机制传递。

共享只读对象不能指向某个 isolate 的可变堆，运行时类型和分派缓存放在 isolate 上下文中。一个 isolate 同时只有一个托管执行者；外部线程不能直接改写其堆指针。跨线程句柄注册与释放必须通过与 GC 同步的注册表或所属 isolate 的调度路径完成。

所有活跃的受管理引用由以下来源提供：

```text
安全点处的栈根槽
ThreadState 中登记的引用
静态或规范对象根
运行时句柄
调度器和原生回调的持有引用
```

初版在可能 GC 的调用之前把活跃 ref 和 tagged 值写入可描述的栈根槽，返回后按寄存器约束重载。根映射同时记录槽位置和表示，原生地址不当作根扫描。安全点允许出现在分配慢路径、需要的循环回边、原生转换与其他显式 poll 位置。

ClassDesc 通过指针位图和变长对象扫描规则描述对象负载。分配器必须先建立可被 GC 安全扫描的对象头和引用槽，才允许下一安全点；语言字段的默认值、late 哨兵和初始化顺序另由标准库与编译代码保证。

指向受管理对象内部的原生地址不能独自跨安全点存活。跨越这类边界必须使用显式句柄与 pin 借用，保证基对象仍然活跃；内部原语的默认规则更严格，禁止这类地址逃逸。基对象与内部地址的关系在更换 GC 算法时尤其重要。[GC 安全点与派生指针](https://llvm.org/docs/Statepoints.html)

初版不采用移动式或并发 GC，因此不需要每次写引用都执行分代或并发写屏障。将来更换收集器需要重新评估安全点、地址借用和屏障，并更新相应 ABI 契约。

WeakReference、Expando 与 Finalizer 的弱边单独描述。收集过程依次完成强引用标记、条件弱映射的闭包计算、弱引用清理与终结排队，再清扫；Dart 终结回调在收集结束后按 标准库调度规则执行，不进入 noGC 扫描核心。

### 异常与栈展开

采用有帧指针的表驱动展开。正常调用直接返回正常值；发生异常时，由运行时查找处理表并恢复到对应 landing pad。

FrameDesc 记录代码区间、帧大小、保存的寄存器与位置、根映射、处理区间、源位置和内联调用位置。可以省略帧的叶函数仍须满足调用链和异常轨迹所需约束。

抛出入口先把异常对象和栈轨迹登记为根，再捕获必要的轨迹并开始展开。实际恢复寄存器和跳转的展开核心是 noGC 路径。finally 的控制流由编译器生成，展开器只定位处理入口，不能替代语言级清理逻辑。

Dart 异常不直接穿过原生 C 栈。回调跳板捕获异常并遵守相应 FFI 接口约定；Dart 中对原生函数的调用异常语义由 标准库和桥接层处理。OOM 使用预留的异常对象和不依赖受管理分配的失败路径。

### 运行时入口

下表采用 ABI 记法，Ref、Value 和 Addr 都是字级表示，不是额外分配的 Dart 包装对象。所有入口通过符号直接调用，不使用字符串操作码或 List 参数的万能分派器。

| 入口 | 逻辑签名 | 契约 |
|---|---|---|
| rt_alloc | ClassDesc、变长负载长度 → Ref | 返回可安全扫描的对象；可能 GC 和抛出 |
| rt_poll | void → void | 检查安全点请求，可能 GC |
| rt_is | Value、TypeRef → bool | 按 Dart 类型语义判断；初版保守允许 GC |
| rt_as | Value、TypeRef → Value | 失败时抛出类型错误，可能 GC |
| rt_invoke_dynamic | receiver、selector、参数描述与向量、类型实参 → Value | 执行分派、参数校验与 noSuchMethod，可能 GC 和抛出 |
| rt_raise | 异常、可选轨迹 → never | 登记根并进入抛出流程 |
| rt_rethrow | 异常、原轨迹 → never | 保留要求的原轨迹并传播 |
| rt_handle_open | Ref → Handle | 在原生边界持有受管理引用；句柄存储不依赖受管理分配 |
| rt_handle_close | Handle → void | 释放显式持有关系 |
| rt_enter_native | ForeignFrame、调用属性 → void | 登记根、线程与回调边界 |
| rt_leave_native | ForeignFrame → void | 恢复托管状态 |
| rt_post_message | 目标、消息 → void | 遵守 isolate 可发送性与复制或转移规则，可能 GC 和抛出 |

这些入口的名字、签名、效果与隐式根需求只在 abi 中定义一次。构建运行时检查实现的效果不得超出声明。新辅助函数作为普通可达符号加入，不需要预先列出所有未来运行时服务。

标准库的 List、Map、String、Future、Stream、Zone 等语义由普通 Dart 类和函数实现。编译器只识别具有明确身份的 标准库内部原语。print 作为 标准库函数处理字符串转换与 Zone 行为，不按文本名字在用户 AST 中直接替换成系统调用。

只有整程序分析能够证明相应条件时，才可以将这类路径特化为更直接的输出，并裁掉不再需要的依赖。

## 纯 Dart 底层实现

### 内建原语

普通安全 Dart 无法独立表达任意内存访问、栈恢复和寄存器跳转，因此目标标准库提供一组私有声明，由本编译器识别并展开为指令：

```text
按宽度的原始 load 与 store
地址、字值和浮点位模式转换
受控制的对象表示访问
原子操作与内存屏障
已知签名的原生调用
线程上下文访问
栈或寄存器上下文恢复与跳转
trap
```

原语是明确的编译契约，只有受信任的标准库和运行时库可以声明；应用不能通过复制一个 pragma 就取得这些权限。声明可以使用标准 Dart 语法、元数据和零包装的内部值类型；其目标语义由本编译器提供。

私有原语声明可以采用如下形式，Word 与 Address 在目标编译时分别使用未装箱字值和 addr 表示：

```dart
extension type Word(int bits) {}
extension type Address(int bits) {}

@pragma('native:intrinsic', 'loadWord')
external Word loadWord(Address address);

@pragma('native:intrinsic', 'storeWord')
external void storeWord(Address address, Word value);
```

这些声明属于目标标准库的受信任输入，不表示官方 Dart 已提供其执行实现。Word 与 Address 进入普通 Object 上下文所需的装箱不能在 noGC 代码中发生。

启动跳板、异常跳板和回调跳板由 Dart 指令编码器生成，无需把手写汇编文件作为另一个实现语言。调用操作系统服务仍然需要平台 ABI 与系统库，这不会消除平台依赖。

编译器与链接器不依赖 C/C++ 编译器、外部汇编器、外部链接器或 LLVM。Mach-O 本地 ad-hoc 签名可在 Dart 封装层实现；证书或设备密钥参与的分发签名作为独立平台打包接口处理，不改变程序 ABI。

### noGC 约束

GC、堆扫描、根遍历、帧恢复及其可达底层函数使用 noGC 约束：

```text
不分配受管理对象
不进行隐式装箱、字符串构造或闭包创建
不调用可能 GC 的函数
不使用会创建 Dart 异常的失败路径
不发生异步暂停
仅访问原始内存、未装箱值和已存在的对象表示
```

标记工作栈和堆元数据使用操作系统提供的原始内存。GC 处理数组、列表和队列时也不能偷偷调用普通 List 或 Map 实现。

noGC 在高层检查一次，并在表示选择和运行时调用展开后再次检查，包括自动插入的装箱或慢路径。已知外部叶函数的属性来自受信任的 ABI 声明；未知原生调用不能被当成 noGC。

这把“运行时需要 GC，而 GC 又需要运行时”的循环切在了可验证的边界上。宿主编译器仍可使用官方 Dart 的 GC；目标 GC 的源码不在宿主 import 图中执行。

### 原生调用与回调

ForeignCall IR 明确携带 C 签名、参数布局、返回布局、可回调性与阻塞属性。目标后端根据 Darwin ABI 生成适配，不把 Dart tagged 值直接当作 C 参数传递。

调用前建立必要根与 ForeignFrame，调用后恢复托管状态。原生代码长期持有的对象通过 Handle 或 Pin 管理，裸整数地址不承担保活责任。

ForeignFrame 至少保存上一托管帧锚点、原生调用边界和句柄范围。回调期间若发生 GC，可通过这些锚点遍历被原生调用隔开的托管帧段，而不尝试把任意 C 栈帧解释成 Dart 帧。

回调跳板进入拥有该回调的 isolate，并遵守 API 对线程和同步返回的限制。异步回调通过消息调度，同步回调的线程限制必须显式检查。动态回调的入口分配、回收与平台执行内存策略属于平台跳板模块，不能隐含依赖任意地址都能执行。

### 原生库导出与 ABI 描述

向宿主导出普通平台 C ABI，不暴露内部 tagged 编码、ThreadState、类描述符或 GC 对象地址。原生类型与目标由已有 FFI 声明提供，例如带显式 NativeType 签名的 Pointer.fromFunction 绑定；构建选项选择要导出的绑定及符号。普通 Dart int、String 或 Object 签名不能作为编译器猜测原生 ABI 的依据。只进行能够证明等价的表示转换；其他转换及所有权由使用者通过 FFI 显式设置。不另造导出 pragma、原生类型体系或默认的自动绑定生成层。

| 导出契约 | 无上下文函数 | 托管组件函数 |
|---|---|---|
| 适用范围 | 可达代码只使用原生值，不需要 Dart 堆、静态托管状态、异常或调度 | 使用 Dart 对象、异常、堆或异步设施 |
| 初始化 | 无 Dart 初始化接口 | 宿主创建并销毁组件上下文，按需启用运行时模块 |
| 参数和结果 | 明确宽度的标量；扩展缓冲区时声明长度、借用和所有权 | 原生值、显式上下文与不透明对象句柄 |
| 线程 | 经证明没有线程依赖或共享可变状态，才允许任意宿主线程直接调用 | 初版上下文固定所属线程；回调、调度与重入另有显式约束 |
| 错误 | 证明不会产生 Dart 异常；其他失败按声明的 C 契约返回 | 边界捕获 Dart 异常，返回状态及显式错误结果 |

无上下文导出不一定是机器码叶函数，但其所有传递可达路径都必须满足该契约。noGC 只能保证不发生收集，不能单独证明无初始化、无异常、无线程依赖或线程安全。表示选择后的隐式装箱、类初始化、间接调用和原生调用效果也必须纳入核验；无法证明就拒绝该导出形式，要求托管入口。

托管组件初版采用一个显式上下文对应一个堆和执行域，内部沿用上述 isolate 语义；不要求执行用户 main。上下文建立入口是普通 C ABI，引导建立 ThreadState 后才进入托管代码。销毁前必须结束活动调用、关闭回调并释放宿主持有的句柄；跨组件堆不互传裸对象。句柄的持有、释放与所属上下文必须可检查。同步导出先使用返回状态、结果输出参数与错误句柄，不让 Dart 异常穿越 C 栈。异步导出的任务、取消与调度契约需单独设计后再启用，不能默认为宿主有 Dart 事件循环。

构建结果可以报告目标、符号和已有 FFI 声明，并核验分配、异常与上下文约束，但不能推断使用者没有声明的内存所有权、错误策略或线程契约。自动生成 C 头文件、ABI JSON 或其他语言绑定不作为当前任务。ABI 版本与语言版本分别管理。有限库验证先支持显式 Int64 标量签名，后续按真实使用需要扩展。

## 按需链接与文件格式

### 依赖图

可执行应用从程序入口建立根；库从显式导出与实际需要的上下文建立、释放入口建立根。两者都保留可达的 isolate 入口、FFI 回调和语言语义要求的保留项；原生导入声明只有被引用时才建立依赖。Dart 顶层与静态字段的初始化按惰性语义由访问建立依赖，不能把全部初始化器直接设成根。默认未知动态调用会保留其可能目标，不能为了体积假装它不存在。
节点既包括函数，也包括类描述符、类型实参、常量、字符串、跳板、处理表与运行时辅助函数。描述符、分派表和 native 注册表在分析后按需求生成，不能先放入完整表，把所有实现都变成可达。

编译器必须显式保留来自原生代码的入口；仅从 Dart 中的显式调用出发不足以保证 AOT 正确性。[Dart AOT 入口说明](https://github.com/dart-lang/sdk/blob/main/runtime/docs/compiler/aot/entry_point_pragma.md)

GC、事件调度、网络和 FFI 等运行时功能通过实际符号需求引入。是否保留 GC 取决于所有可达路径及隐式需求，不能仅检查源文件是否出现 new。

### CodeBundle

后端和链接器的交换结构为：

```text
CodeBundle
  symbols        符号定义、可见性、签名与 ABI 指纹
  fragments      函数、跳板、只读数据与可写数据片段
  references     普通符号边、类型与运行时需求
  relocations    地址、分支、页地址和元数据引用
  metadata       类、帧、根、异常、源位置及导出信息
```

每个片段有权限、对齐、符号锚点和内容。不存在依赖固定 Mach-O 文件位置的前端 IR。ClassId、字段布局和代码地址应使用逻辑身份或可重定位引用；缓存的机器码不能偷偷依赖另一构建中恰好相同的实体编号。

### 布局与封装

链接器解析符号、删除不可达片段、进行安全的代码或常量合并，并组织入口、调用跳板与导入。再迭代计算布局和指令松弛，处理超出范围的分支以及可缩短的寻址指令。

类型元数据、GC 根映射与异常表通过符号锚点共同重定位。机器码变长或缩短后，不能仅修正分支而遗漏这些表。

格式封装器把稳定的 LinkedImage 转成 Mach-O 的段、section、加载指令、绑定和签名。对齐取满足格式、权限和目标约束所需的值；可写零初始化空间允许使用虚拟零填充。正文、数据与签名确定后才计算签名。

相同输入、选项与工具链应产生相同的本地映像。符号排序、实体编号和源码路径必须稳定；UUID 从 UUID 与签名字段归零后的规范化内容导出，再填入 UUID 并计算无时间戳的本地签名，避免哈希依赖自身。证书分发签名不作为编译器确定性比较的对象。

## 自举与验证

### 宿主与目标的构建边界

```text
上一份已验证的本地原生 dartc
  + 编译器源码
  + 目标标准库与运行时源码
  → 新版原生编译器

新版原生编译器
  + 相同源码与目标配置
  → 再次生成的编译器
```

开发中默认复用本地原生种子，只有新工程没有本地种子时才由官方 Dart 编译初始宿主种子。后续重复自编译与行为验证全部通过后，才替换本地种子；已有种子执行失败不能静默回退官方编译。官方编译器另用于行为、产物和性能对照，不参与日常种子更新。当前 CI 仅手动触发，正式发布时再整理可分发的上一代原生编译器资产。

编译器源码维持在选定官方 Dart 能编译的范围。目标标准库与私有原语由新编译器编译，不要求官方 Dart 执行新运行时的原语。编译器自身使用到的 标准库 能力也是自托管验收的一部分，例如文件、编码、集合和进程服务。

引入先行语言功能时，先用上一引导版本理解的写法实现其支持，保留可用源码和二进制节点，再让实现源码开始使用新功能。需要时从历史节点回移修复或临时消去扩展语法，重建引导链。

自编译成功只证明覆盖了自身用到的能力，不等于完整 Dart 兼容。对确定性构建比较后续自编译阶段的结果，同时验证运行行为。

### 必需验证

| 层 | 验证内容 |
|---|---|
| 前端 | 合法与非法程序、名称与类型规则、语言版本、错误位置 |
| SSA | 每个重要变换的合法性与语义差分 |
| 后端 | 指令编码、寄存器约束、调用保存、溢出与跨范围分支 |
| GC | 每个安全点触发 GC、真实根保留、弱引用、终结与原生持有关系 |
| 异常 | 多层调用、finally、重抛、异步边界与轨迹 |
| FFI | 参数与结构体 ABI、回调、线程限制和资源生命周期 |
| 原生组件 | 显式 FFI 签名、C 静态和动态链接、无上下文证明、托管上下文与错误边界 |
| 文件 | 格式、绑定、重定位、签名和真实系统运行 |
| 自举 | 种子构建、重复自编译、官方参考行为和构建确定性 |

优化错误通过单独禁用变换、输出 IR 和最小化差分用例定位。缓存键包含源码、相关依赖、编译器版本、目标、ABI、标准库和优化选项；内联体或分析摘要改变时，使用者也必须失效。

## 架构验收边界

可以据此确定的实现契约是：独立前端、两层 IR、语义类型与表示分离、显式效果与异常边、共享 ABI、精确 GC、noGC 底层、细粒度可达性、符号化代码片段和独立文件封装。

收集器算法、调用约定和对象头是本版方案的选择，不承诺未来二进制兼容。改变这些契约时提升 ABI 版本并整体重建，不增加旧布局适配层。
