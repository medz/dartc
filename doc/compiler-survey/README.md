# 编译器架构与持续自演进调查

## 结论

**dartc 的纯 Dart 原生实现方向有可借鉴的成熟先例；当前实现还不足以据此宣称已建立完整、可持续优化的 Dart 执行基础。** 已有 native seed、SSA/MIR、Dart 运行时算法和差分工具值得保留。接下来最关键的不是寻找一个“更快编译器的目录模板”，而是让语言语义、优化表示、机器约束、运行时内存与引导兼容性成为可检查、可迁移的合同。

研究不建议因为一次基准就推翻后端，也不建议继续仅按语法点累积功能。建议保留独立前端、类型化 SSA、MIR 和原生写出；以语义交接、有限分析/优化、准确 GC/调用协议、明确文件拥有者为依赖顺序推进。具体审查与建议见 [dartc](dartc.md)。

## 范围与证据口径

调研基线：2026-10-27。dartc 审查固定在 `79b22ba0309a14f2d3e1417a121a37b6293dfcd4`。外部项目按各章列出的源码 revision、版本和官方文档核对；开发分支快照不代表稳定发布。未构建或重跑外部编译器，不提供跨语言性能排名。

选择的是主流和有明确架构价值的代表，不是声称穷尽所有编译器的“Top N”。以下三类证据分别使用：

- **源码事实**：固定 revision 中实际存在的表示、调用链、拥有者、构建和测试入口。
- **项目设计/报告**：官方架构文档、作者论文、发布说明；保留原有版本、模式和工作负载限制。
- **dartc 建议**：基于上述事实与本项目目标的工程判断，不把建议写成已经实现的能力。

文件布局调查同时区分源码目录、编译期数据布局、运行时对象布局和产物/ABI 布局。它们有关联，但解决的是不同问题。

## 跨项目比较得到的共同点

### 语言语义不能交给机器后端猜

Rust 的 HIR/THIR/MIR、Swift 的 SIL、Go 的语言 IR/walk、GHC 的 Core/STG、LFortran 的 ASR 各有自己的目的。LLVM IR、Cranelift CLIF 和 QBE IL 并不会替生产者完成语言类型系统、默认实参、泛型、异常或 GC。不同项目的 MIR、FIR 同名缩写也不能当成相同层次。[主流工具链](native.md)、[专门化案例](specialized.md)

这不要求 dartc 复制它们所有层次。最小要求是：每个 lowering 单元的语义义务已有明确结果和拥有者，需要保留的类型、effects、异常/检查、对象身份与源位置不被提前丢掉。结果可以按需计算，但不能靠后续发码重新按名字推测。

### 高性能来自信息、分析与取舍，不来自 IR 名字

SSA 让数据流更可分析，但内联、去虚拟化、装箱消除、范围/别名/逃逸分析、循环变换、指令选择和寄存器分配都需要自己的事实与正确性条件。QBE、Cranelift 和完整 LLVM 的投入边界不同；选择较小优化预算可以合理，不能把它等同于缩小 Dart 语义。[社区后端](community.md)

真实高性能实现还会保留“快编译”和“更好机器码”之间的取舍。调查中的历史数字用于理解这种取舍，不构成 dartc 的预计收益。先有语义正确和可归因的成本，再选择具体优化。

### 自托管与执行基础的实现语言是不同维度

Rust/Crystal 有同语言编译器，Swift 正逐步采用 Swift 编写编译器模块；这些工具链仍依赖 LLVM、C/C++ runtime 或外部 GC。Go 和 GraalVM 提供了更多用自身语言实现底层算法的例子，但也仍有受信原语、平台代码及引导依赖。DMD 的当前 D 后端则是自有机器后端的有用参照。[native.md](native.md)、[managed.md](managed.md)、[community.md](community.md)

因此纯 Dart 不是已被证明的性能障碍，也不是自动获得性能的理由。需要验证的是：Dart 是否能在受约束边界下表达和编译内存/调度算法；这些算法能否在旧工具链支持后安全采用；其生成代码和 runtime 成本能否持续测量、改进。

### 内存合同贯穿编译器与运行时

GC 选择、根、写屏障、安全点、未完成对象、寄存器、异常展开和原生边界是同一协作协议。NoGC/Uninterruptible 等约束的价值在具体可检查义务；它们不是给一段代码打上“安全”标签就结束。[managed.md](managed.md)

非移动 GC 是可以认真研究的路线，Go、Julia 等证明不必把移动式 collector 当成高性能的唯一答案。但它仍需要回收、复用、触发策略和实际存活证据。bump、根枚举和物理区间记录分别只是其中的部分职责。

### 布局以拥有者为依据

成熟项目会把语义、优化、目标后端、运行时和工具分开，但不是都采用同一种目录树。Odin 甚至包含实现文件的组合式构建；Swift 与 Rust 的语义层也不相同。应学习“谁拥有定义、结果和不变量”，不能把文件多、目录深或统一后缀当成架构质量指标。[native.md](native.md)、[community.md](community.md)

对 dartc 而言，现有架构中渐进拆分的方向应保留。每次拆分带走完整职责、定义和调用方，不复制状态、不建立转导壳、不预建空目录。runtime 的拆分必须与原语信任和声明身份一起完成。[dartc 审查](dartc.md#文件布局如何推进)

### 引导应跨越能力变化，而非仅重复构建

需要分别识别宿主编译器自身的 ABI、它消费的目标 runtime、输出产物的 ABI，以及新编译器将支持的能力。Go 的多阶段构建、OCaml 的 runtime/primitive bootstrap 和官方 Dart 的 host/target 布局区分，比一句“旧版编译新版”更具体。[managed.md](managed.md)、[OCaml](specialized.md#ocaml-与-oxcaml)

stage2/3 相同是有用检查，但仍可能共同继承错误；语言行为、独立 oracle、IR/分配局部验证与原生执行提供不同证据，不能互相取代。

## 对 dartc 的建议取舍

| 议题 | 调查建议 | 验证标准 |
|---|---|---|
| 纯 Dart 与独立原生后端 | 保留方向；不因成熟项目复用 LLVM 就推导本项目也必须依赖它 | 语言实现、运行时算法与原生构建链保持可独立修改；不可避免机器能力显式且少量 |
| 前端 | 明确已检查程序/结果表与 lowering 的交接，继续实现一般 Dart 语义 | 未使用声明也满足应有静态义务；lowering 不重复猜测绑定/类型；SDK 对照覆盖组合行为 |
| IR | 保留类型化 SSA 与 MIR，按实际合同分阶段；不预建通用 IR 框架 | def-use、支配、边实参、类型、effects、异常/根信息等不变量可检查 |
| 内存与调用 | 优先完成与生成代码一致的协议；不先承诺某种 GC 一定提速 | 引用跨调用/分配存活、未完成对象安全、可回收复用、原生边界与真实内存趋势 |
| 引导 | 保留本地种子和匹配 runtime，能力支持先于源码采用；ABI 改变有桥接步骤 | 旧→桥接→新→自重建可恢复，行为与匹配关系真实验证，版本不匹配不静默混用 |
| 文件布局 | 按职责渐进迁移已有实现 | 定义单一拥有、直接导入、明确输入/输出；目录移动不计作语言完成 |
| 优化 | 在语言开发同时按热点做有界增量，不先上全套复杂分析 | 同一行为/工作量下记录编译、启动、执行、内存和体积；能定位回归，不降低语义换数字 |
| 验证团队 | 语义/运行时/后端围绕可交接合同并行，集成者审查交互 | 小而完整的变更、精确反例、实际重放、相应平台执行；main 只集成验证增量 |

这些建议是架构决策依据，不是当前实现能力；现有架构和语言 specs 继续分别拥有设计与实施状态。

## 关于性能结论的边界

一次自编译任务不能判断编译器在所有程序上“全面落后”或“整体更好”。它能回答的是该任务、该源码和 runtime、该平台与模式下的成本。成熟度、语言兼容性和性能应分别评估。

同一份 dartc 源码由 SDK AOT 与 native dartc 构建，再执行相同任务，可以帮助研究宿主 codegen/runtime 差异；其程序算法相同，不能直接把执行差距归因为缺少某个未用到的语言特性。两套编译器分别编译同一普通程序，则还要考虑各自产物策略和运行时能力。跨语言比较更需要等价的任务与工作量，不能比较不同编译器编译各自源码的秒数就排出通用名次。

接下来需要的是可区分阶段、生成代码和分配行为的代表性任务集，不是将项目首页的倍数拼成排行榜，也不是在提交文档中维护一次性的性能成绩。
