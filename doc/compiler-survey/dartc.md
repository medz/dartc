# dartc 的持续演进能力审查

审查源码基线为 [dartc@79b22ba](https://github.com/medz/dartc/tree/79b22ba0309a14f2d3e1417a121a37b6293dfcd4)。架构目标见 [architecture.md](../architecture.md)，语言状态仍以 [specs](../../specs/README.md) 为唯一维护位置。本文审查模块契约和演进条件，不复制逐项语言状态，不将未合入的本地候选计入能力。

## 判断

**现有实现可以作为继续演进的原生工具链起点；已有证据不足以证明它已经形成能长期优化完整 Dart 实现的基础。**

这两句话并不矛盾。编译器、运行时算法和发码器确实由 Dart 表达，原生编译链也确实存在；主要风险是阶段之间尚有隐式依赖，语言语义与表示决策交织，内存回收未落地，部分接口依赖固定来源和名字。继续逐项添加语法，而不改善这些交接契约，会增加后续语言实现、运行时替换和优化验证的成本。这是源码审查得到的工程判断，不是通过一次基准推导出的因果结论。

## 当前真正执行的流水线

入口 [driver/command.dart](../../lib/src/driver/command.dart) 调用：

```text
collectSources
  → parseSource：解析、声明/局部绑定、类型/流/常量检查及 lowering
  → 带类型信息的栈式指令序列
  → buildSsa
  → optimizeSsa
  → reachableFunctions、NoGC 检查
  → selectMachine、NoGC 机器层检查
  → allocateRegisters
  → generateCode
  → createExecutable / createLibrary
```

因此，当前并非“AST 直接发机器码”，也并非“架构文档里的完整前端、优化器和运行时已经实现”。栈式表示目前是构造 SSA 的过渡载体；长期是否保留它，应由语义完整性、源位置保存、编译成本和维护成本决定，而不是为了满足某个 IR 数量。

## 源码事实与影响

| 边界 | 当前事实和拥有者 | 对演进链的影响 |
|---|---|---|
| 源码与库 | [source.dart](../../lib/src/source.dart)、[source_uri.dart](../../lib/src/source_uri.dart)、[package_config.dart](../../lib/src/package_config.dart) 保存文件/库、URI、版本和配置；[symbols.dart](../../lib/src/symbols.dart)、[binding.dart](../../lib/src/binding.dart) 已有声明和局部绑定身份 | 已有一般库模型的起点；后续必须把声明身份延续到类型、调用和运行时角色，不能回退为拼接源码或全局按名字猜测 |
| 语义交接 | [frontend.dart](../../lib/src/frontend.dart) 同时协调声明、推断、流事实、常量、调用适配和指令生成；[typing.dart](../../lib/src/typing.dart) 等拥有部分独立规则，但没有完整、可独立消费的已检查程序结果 | 新特性容易同时修改语义和发码；未使用代码的错误检查不能被可达性删除取代。先形成显式语义结果，再决定哪些 lowering 可以复用 |
| 类型与表示 | [types.dart](../../lib/src/types.dart) 拥有语义类型；[machine.dart](../../lib/src/machine.dart) 将其映射到 I64、I1、Addr、Ref、Tagged | 已经有分离，不能说完全没有；当前表示集合和调用约束仍有限，不能把新增 Dart 类型机械地等同于新增机器 word |
| SSA | [ssa.dart](../../lib/src/ssa.dart) 有带类型的值、块参数、边实参、终结指令及 effects；从局部和栈状态构建控制流与 SSA | 能承载继续优化；但仅有这些结构，不自动提供支配关系、别名、范围、逃逸或异常路径的完整分析 |
| 优化 | [optimize.dart](../../lib/src/optimize.dart) 的主线是布尔检查简化、SCCP、初始零存储消除和死值/块参数清理 | 有真正的优化实现；尚不能据此宣称已有成熟的内联、去虚拟化、逃逸/标量替换、循环优化或向量化管线 |
| 调用 effects | `ssaEffects()` 对普通调用保守赋予读、写、分配、抛出、GC、native effects；[nogc.dart](../../lib/src/nogc.dart) 检查 SSA 与机器层的 NoGC 义务，并在受检调用闭包内传递机器层摘要 | 正确性上比漏记 effects 安全；供一般优化消费的精确调用摘要、失效规则和跨阶段证明仍需建立，不能直接把保守标记删掉 |
| 合法性验证 | 当前入口没有在各个变换边界调用统一的 SSA/MIR 结构验证器；SSA 构造、根表和 NoGC 各有自己的错误检查 | 这些检查各有价值，但不等同于验证定义唯一、使用受支配、边/块参数类型、效果和 GC 位置的一般 verifier |
| 寄存器与根 | [allocate.dart](../../lib/src/allocate.dart) 为 I64/I1/Addr 分配 x19–x27；Ref/Tagged 留在 spill 槽；[root_map.dart](../../lib/src/root_map.dart) 在调用点要求活跃托管根落栈 | 这是保守的分配策略，调用点根图按活跃性和表示种类精确枚举，并非猜测指针的 conservative GC。若允许引用进寄存器，分配、调用 clobber、根位置和扫描器必须一起变更；当前性能影响大小尚未归因测量 |
| 边复制与发码 | [emit.dart](../../lib/src/emit.dart) 通过 push/pop 实现位置不同的边参数并行传递；机器层仍含 ARM64 条件码等目标信息 | 有正确性优先的实现；并行复制、指令约束和目标信息的拥有者可继续细化。不能把改善复制策略等同于重新设计整个中端 |
| 分配与回收 | [runtime.dart](../../lib/src/runtime.dart) 的 `rtAlloc()` 使用 bump arena，记录物理分配边界；有根与对象边枚举，没有正式启用的标记、清扫、空闲复用或 arena 释放 | 不能稳定支撑长期存活程序的内存成本。回收策略必须同时验证存活、NoGC、构造未完成窗口、原始地址和回收复用；“有根表”不等于“有 GC” |
| 算法的实现语言 | String/List、分配器、对象访问、类型检查及系统适配的大量算法是 Dart；ARM64 指令由 Dart 编码 | 纯 Dart 演进方向有实际基础。问题是如何缩小可信边界、提高一般语言能力和可替换性，不是必须改写成 C++ 才能继续 |
| 原语与运行时角色 | runtime 顶部有显式原生存取/调用/系统服务声明；前端检查受信来源和签名；[abi.dart](../../lib/src/abi.dart) 仍以 runtime 来源编号 0 和函数名寻找实现 | 原语命名表可以是明确的内部协议；固定物理文件身份则会妨碍运行时模块化。应绑定真实声明与角色/签名，而不是把所有同名函数或整个库授予权限 |
| 状态所有权 | `ir.dart`、`frontend.dart`、`format.dart` 等持有构建级可变列表和全局状态 | 单次进程构建可以工作；分阶段重放、隔离分析、并行编译和缓存失效更难。改进应逐个建立 phase/program/function 的实际拥有者，不先造通用编译会话框架 |
| 产物和链接 | [reach.dart](../../lib/src/reach.dart) 已做函数/运行时需求可达性；[format.dart](../../lib/src/format.dart) 同时处理常量/类型/根元数据布局和文件封装 | 按需运行时并非空白；符号需求、重定位和最终地址布局仍应与 Mach-O/ELF 写出逐步分开，避免把语义或可达性重新埋进封装器 |

这些事实不能单独证明某项是当前性能差距的主要原因。引用落栈、装箱、边复制、线性查找、String/List 分配与无回收都值得测量，但源码上“看起来贵”不能代替同任务的热点、分配量和阶段成本证据。

## “Dart → 改进 Dart → 再改进 Dart”需要什么

### 三条不同的循环

1. **构建循环**：旧原生编译器构建新源码，新编译器再构建自身。已有 bootstrap 验证这条循环的一部分。
2. **能力循环**：旧版本能实现新语言或原语的编译支持，再由新版本编译开始使用该能力的编译器/运行时源码。必须有明确迁移顺序和恢复点。
3. **改进循环**：行为保持一致，同一任务的成本改善，并且未来语言/运行时变更仍能被验证和定位。它需要语义结果、IR 契约、运行时协议及有代表性的测量。

第一条成功不能证明后两条自然成立。也不能只比较新编译器编译自身更快：需要分别识别实现算法变化、生成代码质量变化和运行时成本变化。

### 使用新语言能力改进自身

应该这样做，但分开验收可读性、正确性和成本。已有普通类足以开始表达构建/函数状态的实际拥有者；以后一般泛型、Map/Set、records、枚举或模式可以简化查找、成组数据和穷尽处理。不能只实现编译器刚好使用的几种拼写，也不能因为写法更新就假设分配更少或执行更快。

每次采用先由旧种子构建支持该能力的编译器，完成一般正反行为验证，再让编译器或 runtime 源码使用它。新抽象引入的装箱、闭包捕获、动态调用和对象生命周期仍是正常优化对象；不能用针对编译器源码的名字/类型特判来抹掉其成本。

语言能力与优化还应互相检验：泛型的真实类型参数和运行时检查必须保留，共享代码/特化再按任务选择；捕获与异常一旦成为合法程序行为，活跃值、effects、根与控制流分析都需要相应成立。这样才形成一般 Dart 能力改进 Dart 实现的链，而不是越来越多自编译专用补丁。

### 当前 bootstrap 的保证及空白

[tool/bootstrap.dart](../../tool/bootstrap.dart) 优先复制本地种子，构建 stage1/2/3，比较 stage2/3 字节，执行行为测试，成功后替换种子。已有种子失败不会默默回退到官方编译器。这是有用的可恢复基础。

它尚不证明：

- 所有 Dart 语义正确，或编译器使用范围以外的程序都能正确编译。
- 两个相同的后代没有共同继承同一个错误。对照 SDK、独立行为 oracle 和已知反例仍然必要。
- 运行时布局、调用 ABI、元数据和原语集合改变时，旧种子一定能跨越版本边界。
- 多线程、异常展开、捕获环境、一般泛型等新增能力会自然适配当前根与表示协议。

当前 [layout.dart](../../lib/src/layout.dart) 与前端采用 ABI 版本检查。**严格拒绝不兼容输入是必要防线，但不是迁移协议。** 以后变更 ABI 时，需要区分种子自身运行所用的 runtime、它正在编译的目标 runtime，以及新编译器将支持的目标 ABI。共享一个源码路径不证明三者兼容。

建议的迁移验收是具体的：旧种子 + 旧 runtime 构建桥接编译器；桥接编译器支持新约定；再构建采用新约定的 runtime 和编译器；新版重建并执行真实行为，保留前一组匹配的源码、二进制和契约。兼容内容由实际变更决定，不预建多版本 ABI 框架。对照实例见 [OCaml bootstrap](specialized.md#ocaml-与-oxcaml) 与 [Go/GraalVM](managed.md)。

## 语义交接应先收敛，而不是增加空层

建议的最小已检查程序可以是现有 AST 加上由语义阶段拥有的结果表：声明身份、绑定、类型/流事实、常量/默认值、调用目标/实参绑定、必要动态检查与语言版本结果。它不一定需要复制整棵树，也不一定需要第三套可优化 IR。

交接之后，lowering 消费已经确定的语义，保留源位置、异常/失败义务和 effects；表示选择再决定是否装箱、是否共享泛型代码、如何调用运行时。不能在发码时重新猜测某个名字到底是类型、函数、getter 还是构造器。

SSA 到 MIR 之间允许多个明确阶段，而不要求每阶段都建立新 IR 类层次。只有确实需要新的不变量和消费方时才增加表示。参考 Rust/Swift 的语义层、Go 的 walk/SSA 边界，以及 Flang/MLIR 延迟丢弃高层信息的原因，见 [主流工具链](native.md)、[运行时工具链](managed.md)、[专门化案例](specialized.md)。

## 文件布局如何推进

保留现有架构的目标文件布局。调查支持按真实职责迁移的方向，不支持一次性搬完目录或按行数平均拆文件。

| 迁移单元 | 应同时移交的内容 | 完成证据 |
|---|---|---|
| 前端语义 → lowering | 规则的拥有者、已检查结果、调用方直接导入 | 同一语义可独立检查；lowering 不再重复判定；原有正反行为保持 |
| runtime 单文件 → 内存/类型/平台模块 | 原语信任声明、函数角色、签名、布局和依赖 | 普通 helper/part 不获得额外权限；旧种子按迁移顺序构建；真实执行通过 |
| SSA → 分析与具体变换 | IR 定义、分析结果与失效范围、每个变换的前后条件 | verifier、差分行为和真实成本能定位变换影响；没有复制第二套类型/effect 规则 |
| MIR → ARM64 | 机器表示、寄存器类、调用约束、栈与根交接 | 引用在调用/分配处存活；参数与并行复制正确；源语言不依赖文件格式 |
| 链接 → 文件格式 | 符号、片段、重定位和已布局映像 | Mach-O/ELF 写出消费同一明确结果，不再反向决定语言行为 |

目录不是优化成果；阶段契约、定义拥有者和实际调用方才是迁移单元。内部直接导入拥有者；公开标准库的 library/export 组织有语言语义，不能与无意义的内部转导混为一谈。

## 验证与测量还差什么

现有行为测试、SDK/hosted/native 三路差分、保存/重放/缩减工具，以及独立资源采样都是可用基础；调查不建议重新造一套测试平台。

仍需要建立的是：

- 明确的 SSA/MIR 不变量及有意损坏 IR 时能失败的验证；验证结构不能替代语义差分。
- 代表性任务：编译器自身以外的计算、String/集合、分配存活、动态/泛型调用及真实应用。每个任务先定义结果和必要副作用。
- 分开记录编译阶段成本、生成程序启动、稳定执行、分配总量/存活量、内存高水位及体积。CPU、wall 和 RSS 不能互相替代。
- 区分算法和表示的改变：同源码/同算法的 hosted/native 对照，不能直接归因为“语言支持更少”；一般程序的 SDK/dartc 对照，也不能要求不同编译器生成相同机器码。
- 降噪、跨平台实际执行和规模变化；先寻找趋势和热点，再选择内联、逃逸分析、范围分析、GC 策略或寄存器改进。

当前普通程序基准是首次启动每个新产物，含加载和进程启动，未清空文件缓存；它不是稳定吞吐测试。RSS 记录 child 高水位而非并行进程树之和。保留这些口径比给单点数字加更多小数更重要。

## 建议的依赖顺序

以下顺序描述实现之间的依赖关系：

1. 固定语言行为和阶段交接：把语义检查结果与 lowering 的职责分清，补 IR/调用/effect/根的可检查合同。
2. 以一个完整职责做文件拆分，同时处理 runtime 声明身份和真实直接导入，验证旧种子仍可构建。
3. 在这些边界上继续实现语言和标准库；新增语言能力通过旧工具链支持后，再用于简化编译器本身。
4. 完成受约束但真实的回收/复用闭环，验证存活与失败行为；不将 bump 或边枚举当成 GC 完成。
5. 按代表性任务的热点逐项改进表示、调用、分配、代码生成和算法。优化无需等待整个语言完成，但不应先猜一个大型优化项目，再寻找能证明它的用例。

调查不支持缩小 Dart 目标，也不支持仅因当前差距就改用官方 VM 包装或把整个后端长期交给非 Dart 工具链。它支持先把已经存在的原生实现整理成可以明确检查、替换和迁移的执行基础。
