# Developer tooling

Run these commands from the repository root with your installed Dart SDK on macOS or Linux with ARM64/x86-64. [Build the native compiler](../README.md#build-from-source) first; bootstrap verifies and saves `build/dartc-seed` for subsequent runs. Reports record the SDK version actually used; upgrading the SDK also upgrades the reference compiler for new comparisons.

Bootstrap builds stages in a fresh directory and publishes them after the stage2/stage3 byte comparison and behavior checks pass. A code-generation change can make stage1 differ from stage2. Stable self-rebuilds, language behavior and performance each require their own evidence.

Before generating resources, bootstrap records the compiler/runtime source dependencies for both source platforms, the public Export module, validation sources and package-configuration search paths. The native seed compiles `tool/bundle_compiler.dart`; this helper generates an ordinary Dart entry containing the source resources. Bootstrap checks the frozen inputs after generation, each stage and behavior validation; changed inputs prevent publication. On failure, the retained work directory contains the input seed, partial builds and `inputs.json` with the original file contents and SDK version. Keep inputs unchanged throughout the run; these checks occur at phase boundaries.

Successful bootstrap also saves `build/compiler.dart` and `build/bootstrap-inputs.json`. Use that generated entry when cross-compiling the same compiler. To build without an SDK orchestration process, use a matching native seed:

```sh
mkdir -p build
build/dartc-seed tool/bundle_compiler.dart --std lib/src/runtime.dart -o build/bundle_compiler
build/bundle_compiler "$PWD" build/compiler.dart
build/dartc-seed build/compiler.dart --std lib/src/runtime.dart -o build/dartc
```

Regenerate the entry after editing bundled sources or moving the checkout. Preserve a verified seed and its source revision together for recovery. `--std` selects external sources for development; the resulting compiler embeds the resources generated above. Native archives contain the binary, license and usage notes. `test/package_release_test.dart` checks the binary alone with the original source path removed, explicit source overrides and package mappings.

Behavior tests compare real compilation and execution with the SDK, including exit status and declared output files. Independent cases run concurrently using the environment's available CPU count. Add cases to the owning fixture or rejection group, give concurrent cases separate source and output paths, and keep tests that mutate shared package configuration in sequence. On failure, active cases finish before the harness preserves sources and process evidence.

## Compare compiler performance

Compare two existing native compilers on the same compiler task:

```sh
dart tool/benchmark.dart --compare /path/to/baseline /path/to/candidate
```

Running `dart tool/benchmark.dart` with no options builds the compiler with native dartc and the official SDK, then compares their execution on the same self-compilation task. Reference binaries never become bootstrap seeds.

Both compiler comparison modes require unchanged inputs and identical generated bytes. Code generation changes need separate behavior and performance comparisons.

## Compare program performance

Compare an ordinary program with the official SDK:

```sh
dart tool/benchmark.dart --program example/hello.dart --seed build/dartc-seed
```

This mode measures compilation and execution separately, with one warmup and four paired rounds, and records artifact sizes. Each newly compiled artifact must run successfully with identical stdout, stderr and declared output-file contents. The SDK and dartc executables may contain different bytes.

To compare a compiler or runtime optimization on the same program:

```sh
dart tool/benchmark.dart --program example/hello.dart \
  --compare /path/to/baseline/dartc /path/to/candidate/dartc \
  --baseline-std /path/to/baseline/lib/src/runtime.dart \
  --std /path/to/candidate/lib/src/runtime.dart
```

This runs the baseline, candidate and official SDK in the same batch. Four measured rounds alternate the two native compilers and balance their positions relative to the SDK. Reports identify each compiler, runtime dependency graph and host ABI, with separate compilation and execution measurements. All three must agree on behavior before the report is accepted; generated bytes may differ.

Use runtime sources matching each native compiler. `--std` selects the candidate runtime in comparison mode, or the single native runtime with `--seed`; `--baseline-std` selects the baseline runtime. Each omitted runtime option defaults to this checkout's `lib/src/runtime.dart`. `--compare` and `--seed` cannot be combined.

- Pass program arguments after `--`.
- Declare task data with repeated `--input <relative-file>` and results with `--check-output <relative-file>`. These paths belong to an isolated task working directory populated from the inputs.
- Compilation reads original source paths. Dependency hashes are checked before and after measurement, and evidence snapshots are retained in `build/`.

Program execution measures the first launch of each new artifact, including loading and process startup; file caches are not cleared. Use a workload that performs enough work for the execution cost you want to compare.

## Resource measurements

Reports record elapsed time, user/system CPU time and kernel peak RSS. Each task uses a fresh sampling process; sampling driver startup and bookkeeping are excluded. Unavailable metrics remain null. Peak RSS is the maximum child high-water mark, not total concurrent process memory.

## Differential testing

Generate bounded integer/boolean expressions, constructor calls and generic-alias interactions:

```sh
dart tool/fuzz.dart --seed 1 --count 20
```

Each case compares the SDK oracle, SDK-hosted dartc and native dartc. Failures retain the actual sources, dependencies, commands and a frozen compiler/runtime/tool snapshot under `build/fuzz/`.

Cases must keep program dependencies inside `project/`. Dependency checks cover the SDK-selected files and the frozen compiler's native-target source graph, including conditional imports selected differently by the two compilers. The native engine must match that compiler source. A pass compares exit status, stdout and stderr; use program benchmarks with `--check-output` for file-output contracts.

Replay requires the recorded SDK version, platform and toolchain fingerprints. An SDK upgrade is a new comparison context; it does not change an existing finding.

To investigate a saved failure:

1. Run the printed replay command. It uses the recorded files rather than regenerating a program from its seed.
2. Add `--shrink` to that command to reduce a generated case. Reduction requires a stable failure and a saved model that matches the source.
3. Check a repaired compiler against the saved case:

   ```sh
   dart tool/fuzz.dart --compiler /path/to/repaired-dartc --case /path/to/saved-case
   ```

Use `dart tool/fuzz.dart --help` for explicit rejection and runtime-failure contracts.

## CI

Run the checks available on the local host and in Docker first. Each supported system requires actual execution; identify emulated runs explicitly. Use CI for remaining platform coverage and appropriate validation batches. Required CI checks must pass before a release. Validation evidence is stored inside a tar archive so legal source paths such as `a:b.dart` survive artifact upload.

The [native self-hosting workflow](../.github/workflows/native.yml) is manually dispatched. Select Linux ARM64, x64 or both, or `macos-x64` for an Intel Mac, with `architecture`, and the reference SDK version with `dart_sdk`. The Linux jobs bootstrap on the selected hosts, run native-library, differential, SSA verification, resource-measurement, program-benchmark and fuzz tests, and cross-compile the compiler for macOS. Release packaging and verification are optional workflow inputs. Use `cross_ref` to supply matching native seeds named `dartc-linux` for Linux ARM64, `dartc-linux-x64` for Linux x64, or `dartc-macos-x64` for Intel macOS. These seeds can be cross-compiled by an existing native compiler; the selected host then executes the complete bootstrap and behavior checks. Only a checkout without a supplied seed uses the SDK for the initial cold bootstrap.

The Intel Mac job runs on `macos-15-intel`, rebuilds the native compiler through three stages, and runs the shared behavior, differential, SSA, resource-measurement, benchmark and fuzz checks. It also executes C callers against object, static and dynamic library output, cross-compiles the compiler for the other three targets, and optionally verifies a relocatable macOS x64 archive. Cross-compiled artifacts still require execution on their target hosts.

## Native archives

Build and check an archive with a native compiler from the same source revision:

```sh
dart tool/package_release.dart --compiler build/dartc-seed
dart test/package_release_test.dart --compiler build/dartc-seed
```

The native compiler already contains its runtime and core-library source dependencies, including imports, exports and parts. The archive adds the license and usage notes. The extracted compiler is checked through direct execution, PATH lookup and a symlink with the SDK removed from PATH. The regression test adds transitive dependencies, builds an archive, and compiles with its binary alone after removing the original source path. It also checks explicit source overrides and package mappings.

## Release notes

Keep `CHANGELOG.md` newest first. Each version has a date, a comparison link and a short description of its user-visible scope. Group entries under Features, Fixes and Upgrade headings as needed; omit empty sections. Combine related commits into one behavior change, and describe fixes by their trigger and observable result.

A GitHub Release starts with what the version enables, then expands its main capabilities with short runnable examples. Follow with upgrade steps, platform downloads, installation instructions and links to the full changelog and versioned specs. Patch releases can use a shorter form. Keep the release and changelog consistent without repeating every entry.

Keep each prose paragraph, list item and blockquote paragraph on one source line so the page can wrap it to the available width. Preserve structural newlines in headings, lists, tables and code blocks.

Explain breaking changes before the examples when users must act. State the affected versions and the concrete replacement or migration step. For compiler/runtime changes, identify the matching archive or bootstrap seed. Validate every example with the reference SDK and the native compiler before publication.

Only include performance claims backed by the same task and necessary side effects; name the compared versions, platform and measurement scope. Keep raw measurements, build logs and validation records in `build/`. Internal refactors belong in release notes only when their user-visible effect can be explained. Language conformance and gaps remain owned by `specs/`.

## Docker cross-target validation

On an ARM64 Mac, keep Linux outputs separate from the Mac seed:

```sh
mkdir -p build/linux-x64
build/dartc-seed build/compiler.dart --target linux-x64 --std lib/src/runtime.dart -o build/linux-x64/dartc
docker run --rm --platform linux/amd64 -v "$PWD:/src:ro" -v "$PWD/build/linux-x64:/out" -w /src dart:3.13.7-sdk bash -ec '
  env -i PATH=/usr/bin:/bin /out/dartc tool/bundle_compiler.dart --std lib/src/runtime.dart -o /out/bundle_compiler
  env -i PATH=/usr/bin:/bin /out/bundle_compiler /src /out/compiler.dart
  env -i PATH=/usr/bin:/bin /out/dartc /out/compiler.dart --std lib/src/runtime.dart -o /out/stage2
  env -i PATH=/usr/bin:/bin /out/stage2 /out/compiler.dart --std lib/src/runtime.dart -o /out/stage3
  cmp /out/stage2 /out/stage3
  dart test/behavior_test.dart --compiler /out/stage2 --std /src/lib/src/runtime.dart
'
```

Repeat with `linux-arm64` outputs and `--platform linux/arm64` for Linux ARM64. The SDK runs the validation harness and reference programs; native stages use the supplied compiler. Keep the SDK version aligned with [specs](../specs/README.md). Publish a verified seed only on its matching host platform, with the corresponding source revision.

Docker on ARM64 executes amd64 programs through emulation. This validates executable behavior and the native build chain; report these runs as emulated. CPU, RSS and timing conclusions about x86-64 hardware require a native x86-64 host.
