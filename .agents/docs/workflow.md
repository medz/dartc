# 开发、审查与知识维护

本文规定协作与验收方式，不授予新的任务权限。任务范围和用户最新指令优先；
文档维护不恢复暂停的编译工作。信息的唯一维护位置见[文档索引](README.md#信息归属)。

## 开始与推进

读取 AGENTS、相关[任务卡](board.md)、必要设计和 skill，再检查当前源码与 diff。
明确原始行为、验收输入、责任拥有者及需要迁移的消费者；不让已有实现或作者说明替代原始要求。
使用 [development-cycle](../skills/dartc-development-cycle/SKILL.md) 完成生产能力；
验证选择与资产复用按[测试说明](../../test/README.md)。

任务卡维护当前负责人、依赖、编辑边界、验收条件与状态；状态定义只在看板维护。
依赖指可消费的合同或产物，不默认等待上游整个领域完成；接口必须共同改变时明确整合负责人。
受阻记录缺失产物和解除条件，继续独立的已授权工作。实际缺项留在原任务，不能拆成后续卡后宣称原交付完成。

## 协作与整合

按实际工作选择并行调查、实现、验证和审查，使用当前环境可用的能力。
分工随依赖和结果调整，文档不规定固定 profile、团队人数、模型、递归层数或每个代理的任务数。
主线程承担关键路径和最终整合，不只转发子代理结论。

分派时明确目标、输入、修改边界、输出和验证责任，避免相互覆盖共享文件。
返回结果包含证据、修改与未决问题；有独立结果即可整合，不建立整轮等待屏障。
共享构建输出与基准测量须协调，防止覆盖资产或因并发资源争用污染测量。

Git 集成由当次交付负责人执行，只暂存本任务内容，保留其他参与者的修改和作者身份。
分支与提交授权遵循 AGENTS 和当前指令。暂存、提交、推送或发布不能冒充行为验收。

## 独立审查与驳回

能力实现/重构、架构或性能的完成声明，以及纠偏规则的效果验收，使用
[dartc-review-delivery](../skills/dartc-review-delivery/SKILL.md)。措辞或格式修正按实际影响核查，
不扩大为无关的编译器全量审计；此门不增加用户批准步骤。

1. 实现者提交原始要求、验收范围、实际版本与 diff 指纹、固定输入/配置、证据、清理结果和剩余缺项。
2. 审查者不参与被审实现，优先使用只获得必要原要求与原始材料的新上下文。不得预设方案正确或诱导通过，作者说明仅是待核查声明。
3. 审查独立核查关键依据，返回接受、驳回或证据不足，绑定具体版本和范围；自查不能替代独立审查。没有独立审查者则留待验收并说明缺口。
4. 根因未修、合同被绕过、必要执行未验、消费者/清理缺失或完成声明与证据冲突，阻止对应任务关闭及作为已验收成果集成、提交或推送。明确授权的阶段保存须准确标明未验收。
5. 驳回返回原任务，在已有授权内修复；不为必要修复再次索取许可。新改动使受影响结论失效，只复核受影响部分并复用有效证据。

实现者可提交反证，审查者必须回应。主线程不能用进度压力、既有投入或另一份赞同覆盖未解决的阻塞发现；
只有用户可以调整原验收范围。证据不足不得写成通过，也不得捏造失败来显得严格。
完成声明被证据否定时，明确撤回不成立的部分，分别完成代码修复和报告纠正；保留有依据的局部成果。
审查措辞直接指出误导陈述与相反证据，不需要猜测作者动机，也不能因无法证明动机而放过问题。

## 根因与规则的拥有者

合同缺失、同类补洞、重复状态、生成阶段猜语义、基础能力一旦执行就恢复沉重形态，
或跨域协调持续扩大，都要求追到真正拥有者。用原反例说明原因及修复机制，比较修复/替换的正确性、迁移、清理和成本。
停止只隐藏该问题的补丁路线，同时继续独立已授权任务；既不默认当前架构正确，也不把大重写本身当成正确性证据。

能由类型、IR verifier 或合同测试可靠拒绝的错误，应落实到代码拥有者。
若当前只授权文档工作，准确登记缺失的执行约束，不以清单、自写通过标记或新规则声称机器约束已实现。

## 自动知识维护

知识维护是实现、调查、审查与返工的组成部分，不等待用户再发一次“整理文档”指令。
出现以下新信息时自动使用 [maintain-knowledge](../skills/dartc-maintain-knowledge/SKILL.md)：

- 用户决定改变目标、约束或已采用设计；
- 验证发现合同、说明或验收声明不成立；
- 同类错误、重复劳动或误导性交付暴露可定位的共同原因；
- 新能力需要可复用方法，现有 skill 缺失、过时或触发不准确；
- 实现替换了现有文档描述的职责、接口或工作流程。

先区分规则未加载、未执行、规则错误和实现能力不足，修改真正造成失败的层。
长期边界、当前设计和重复操作分别进入其唯一拥有者；skill 必须有可识别的触发、必要输入、执行方法和可检查结果。
禁令针对已确认的错误决策，说明拒绝条件；不追加泛泛的“以后注意”，不把单个 API 例子变成专用编译规则。

同一交付中完成：核实依据 → 更新或创建必要的规则/skill → 删除被替代和冲突的内容 → 迁移所有引用 → 验证。
过时说明直接退出当前文档，修改过程由 Git 保存；不另设历史章节或重复复盘台账。
没有新信息就不制造文档。维护须改变下一次行动，而不是增加需要阅读的材料量。

检查相对链接、skill 格式、公开可读性与规则冲突。影响纠偏效果的流程变化用独立的正反例检查；
mock 只能证明该流程在所给材料上的表现，不能证明生产实现已修复。
交付报告区分规则更新、实际执行和未验证部分。下一次同类任务没有改善时，继续修订或删除无效方法。

共享合同与 skills 随仓库维护；原始日志、测量和临时原型可留在忽略目录。
交付证据要让审查者可取得，不能只提供其他参与者无法访问的本机路径。
